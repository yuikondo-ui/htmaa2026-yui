Module 0

Arduino in the embedded landscape

Before the language, know where it sits.

The HTMAA group assignment asks you to compare toolchains and development workflows for embedded architectures. "Arduino" is one of those toolchains. It is worth being precise about what the word means, because it refers to three different things:

  • The boards (Uno, Nano, …) — but you are not using one. You're using a Seeed XIAO RP2040, a tiny board built around the Raspberry Pi RP2040 chip (dual-core ARM Cortex-M0+, 264 KB SRAM, 2 MB flash).
  • The Arduino language — really just C++ plus a library of friendly functions (digitalWrite, delay, Serial.print…). That's what this curriculum teaches.
  • The Arduino IDE + toolchain — the editor that compiles your C++ into a .uf2 machine-code file and uploads it to the chip.

The workflow, end to end

Every embedded platform follows the same loop. In Arduino terms:

  1. Write a sketch (a .ino file) in the IDE.
  2. Compile — the toolchain (GCC for ARM) turns your C++ into RP2040 machine code.
  3. Upload — the code is copied into the chip's flash. On the XIAO you enter bootloader mode by holding BOOT while plugging in (or double-tapping reset); it appears as a USB drive and the .uf2 is dropped onto it.
  4. Run — the chip reboots and runs your program forever, with no laptop needed.
  5. Observe / debug — blink an LED or print over Serial to see what's happening.
Why this mattersUnlike Python on your laptop, there is no operating system underneath. Your program is the only thing running. It never "finishes" — it loops forever until power is removed. That single fact shapes the whole language.

Other options exist for the same chip — MicroPython/CircuitPython (interpreted, type-and-run, slower), C with the Pico SDK (more control, more setup), Rust. Arduino is the fastest on-ramp, and everything you learn here (pins, timing, serial, I²C) transfers directly.

Module 1

Anatomy of a sketch: setup() and loop()

Every Arduino sketch has exactly two required functions. This is the skeleton of every program you will ever write:

void setup() {
  // runs ONCE when the board powers on or resets
}

void loop() {
  // runs over and over, forever, after setup() finishes
}

The minimal valid sketch. It compiles, uploads, and does nothing — correctly.

  • setup() is for one-time preparation: configure pins, start Serial, initialize the display.
  • loop() is the heartbeat: read inputs, make decisions, drive outputs — again and again, thousands of times a second.

The word void in front means the function returns no value (more on that in Module 9). The () means it takes no inputs. The { } braces hold the function's body.

Mental modelsetup() = getting dressed in the morning (once). loop() = your day repeating on a schedule. Anything you set up wrong in the morning affects the whole day.

The order things happen

  1. Power on / reset.
  2. Hidden Arduino startup code runs (sets up the chip).
  3. Your setup() runs, top to bottom, once.
  4. Your loop() runs, top to bottom. When it hits the closing brace, it starts again from the top. Forever.

Module 2

Syntax rules that trip everyone up

C++ is strict. These five rules cause 90% of a beginner's red error messages.

1. Every statement ends with a semicolon

digitalWrite(LED_BUILTIN, HIGH);   // OK  good
digitalWrite(LED_BUILTIN, HIGH)    // ✗  error: expected ';'

The semicolon says "this instruction is finished." Missing one is the #1 beginner error. Note that { } blocks and #define lines do not take a semicolon.

2. It is case-sensitive

digitalWrite ≠ digitalwrite ≠ DigitalWrite. Only the first exists. HIGH is not High.

3. Two kinds of comments

// single-line comment — everything after // is ignored
/* multi-line comment
   spans as many lines
   as you like */

Comments are for humans; the compiler skips them. Use them generously to explain why, not what.

4. Braces come in pairs

Every { needs a matching }. The IDE's auto-indent is your friend — if the indentation looks wrong, a brace is probably misplaced.

5. Whitespace is (mostly) free

Extra spaces, blank lines, and indentation don't change meaning — they're for readability. (This is the opposite of Python, where indentation is the structure.)

Classic trap: = vs ==A single = assigns ("put this value here"). A double == compares ("are these equal?"). Writing if (x = 5) when you meant if (x == 5) compiles but does the wrong thing. You'll meet this again in Module 7.

Module 3

Variables & data types

A variable is a named box in memory. Because a microcontroller has very little memory (the RP2040 has 264 KB of RAM — generous for a MCU, tiny compared to a laptop), you must tell the compiler what kind of value each box holds. That's the type.

The types you'll actually use

int    count   = 0;        // whole number (on RP2040: 32-bit, ±2 billion)
long   bigNum  = 100000;   // large whole number
float  volts   = 3.3;      // decimal number
bool   pressed = false;    // true or false only
char   letter  = 'A';      // a single character (note single quotes)
byte   raw     = 255;      // 0–255, one byte — great for pin/sensor values

For hardware code you'll also see fixed-width types that state their size exactly — uint8_t (0–255), uint16_t, uint32_t. On a memory-constrained chip, choosing uint8_t instead of int for a small value saves bytes. u = unsigned (no negatives).

Constants: values that never change

Two ways to name a fixed value. Prefer const:

const int TOUCH_THRESHOLD = 6;   // typed, checked by compiler (preferred)
#define TOUCH_THRESHOLD 6       // text substitution before compiling (older style, no ;)

Naming your "magic numbers" like this — instead of scattering a bare 6 through the code — is exactly what let you tune the touch sensitivity in Quentin's sketch by changing one line.

Watch the quotes'A' (single quotes) is one char. "A" (double quotes) is a string of text. They are different types. '5' is the character five (value 53), not the number 5.
ScopeA variable declared inside a function only exists there (local). A variable declared above setup() exists everywhere (global) and keeps its value between loop() passes — that's how you remember things from one pass to the next, like a counter.

Module 4

Digital output: blink the LED

Time for the "hello world" of embedded — making a light blink. This uses three functions and one hardware idea.

The three functions

  • pinMode(pin, mode) — configure a pin as OUTPUT (drive a voltage) or INPUT (read a voltage). Set once in setup().
  • digitalWrite(pin, value) — set an OUTPUT pin to HIGH (3.3 V) or LOW (0 V).
  • delay(ms) — pause for a number of milliseconds (1000 ms = 1 s).

Blink, on your XIAO RP2040

// LED_BUILTIN is the XIAO's on-board user LED.

void setup() {
  pinMode(LED_BUILTIN, OUTPUT);   // this pin will drive the LED
}

void loop() {
  digitalWrite(LED_BUILTIN, LOW);    // LED ON  (see gotcha!)
  delay(500);                       // wait 0.5 s
  digitalWrite(LED_BUILTIN, HIGH);   // LED OFF
  delay(500);                       // wait 0.5 s, then loop repeats
}

Upload this and the LED blinks once per second. This is Quentin's blink_RP2040 in miniature.

Active-low LED — a real datasheet gotchaOn the XIAO RP2040 the built-in RGB LED is wired active-low: the pin must be pulled LOW to turn the LED on, and HIGH turns it off. That's the opposite of a classic Arduino Uno. The core also gives you LED_RED, LED_GREEN, LED_BLUE (each active-low) if you want color. Always confirm polarity from the schematic — this is exactly the kind of detail the datasheet exercise trains you to check.

What HIGH and LOW really are

These aren't magic words — they map to voltages. From the RP2040 datasheet you already read: at 3.3 V logic, HIGH ≈ 3.3 V and LOW ≈ 0 V, and an input reads anything above ~2 V as HIGH. digitalWrite(pin, HIGH) literally connects that pin to 3.3 V.

Try itChange both 500s to 100. What happens? Now change one to 100 and the other to 900. You've just built a duty cycle — the seed of PWM (Module 5's cousin).

Module 5

Timing: delay() vs. millis()

delay() is simple but has a hidden cost: while the chip is delaying, it can do nothing else — it's frozen. If a finger touches a pad during delay(500), you'll miss it. For a blinking light that's fine; for a responsive instrument it's fatal.

The blocking problem

digitalWrite(LED_BUILTIN, LOW);
delay(1000);   // ← board is asleep here. Can't read touch, can't update OLED.

The non-blocking pattern: millis()

millis() returns the number of milliseconds since the board powered on — a clock that keeps ticking. Instead of waiting, you check the clock and act when enough time has passed:

unsigned long lastBlink = 0;   // global: remembers when we last toggled
bool ledOn = false;

void loop() {
  unsigned long now = millis();

  if (now - lastBlink >= 500) {   // has 500 ms passed?
    ledOn = !ledOn;                    // flip the state (! means "not")
    digitalWrite(LED_BUILTIN, ledOn ? LOW : HIGH);
    lastBlink = now;                   // remember this moment
  }

  // ...meanwhile the loop keeps spinning, free to read touch pads!
}

The LED still blinks every 500 ms, but the loop never stalls — it can do other work on every pass.

Rule of thumbLearning / one thing at a time → delay() is fine. Doing several things "at once" (blink + sense + display) → millis(). millis() is the single most important step from toy sketches to real embedded programs.

unsigned long is used because time only counts up and gets large (it rolls over after ~49 days). The ? : is the ternary operator: condition ? valueIfTrue : valueIfFalse — a one-line if.

Module 6

Serial: talking to your laptop

The Serial Monitor is your window into the board. Since there's no screen or console by default, Serial.print is how you see values and debug — you already used it to watch the touch counts climb.

Starting Serial and printing

void setup() {
  Serial.begin(115200);   // open the serial link at 115200 baud
}

void loop() {
  Serial.print("count = ");   // print, stay on same line
  Serial.println(42);         // print, then move to a NEW line
  delay(1000);
}

Open Tools → Serial Monitor and set the baud to match (115200). You'll see count = 42 once a second.

  • Serial.begin(baud) — start the link. Baud is the speed; the Monitor's setting must match, or you'll see garbage. 9600 and 115200 are the common values (the XIAO handles 115200 easily).
  • Serial.print(x) — send text or a number, no newline.
  • Serial.println(x) — same, plus a newline (the ln).
Native USB timingThe XIAO RP2040 has native USB, so the serial port can take a moment to enumerate after upload. If you want to guarantee you see the first messages, you can wait for the port in setup() with while(!Serial){} — but only add that if the board will always be connected to a computer, or it will hang when running standalone.

Formatting a whole row (like the touch demo)

Serial.print(pad0);
Serial.print("\t");   // \t = a tab, lines the columns up
Serial.print(pad1);
Serial.println();      // end the row

That's exactly the shape of Quentin's touch sketch output: one number per pad, tab-separated, one row per loop.

Module 7

Control flow: if / else & logic

Decisions are how a program reacts. "If the touch count is above the threshold, treat the pad as pressed."

if (count > TOUCH_THRESHOLD) {
  Serial.println("pressed!");
} else {
  Serial.println("not pressed");
}

Comparison operators

  • == equal to  ·  != not equal to
  • > greater  ·  < less  ·  >= greater-or-equal  ·  <= less-or-equal

Each of these produces a bool — true or false. That's what if tests.

Combining conditions

  • && — AND (both must be true)
  • || — OR (either can be true)
  • ! — NOT (flips true↔false)
if (pad0 > THRESH && pad1 > THRESH) {
  Serial.println("two-finger chord");   // both pads touched at once
}

Many branches: else if

if (count > 100) {
  Serial.println("hard press");
} else if (count > 6) {
  Serial.println("light touch");
} else {
  Serial.println("nothing");
}

Branches are checked top to bottom; the first true one runs and the rest are skipped.

The #1 logic bug, againif (count = 6) assigns 6 and is always "true." You want if (count == 6). Some people write if (6 == count) so a typo'd = becomes a compile error instead of a silent bug.

Module 8

Loops: for & while

Your board has six touch pads. You don't want to write the same code six times — you write it once and loop. (This is loops inside your program, distinct from the loop() function.)

The for loop

for (int i = 0; i < 6; i++) {
  Serial.print("pad ");
  Serial.println(i);
}

Three parts, separated by semicolons:

  1. int i = 0 — start: create counter i at 0.
  2. i < 6 — condition: keep going while true (runs for i = 0,1,2,3,4,5).
  3. i++ — step: add 1 to i after each pass (i++ is shorthand for i = i + 1).

Result: the body runs 6 times, with i = 0 through 5. Starting at 0 (not 1) is a universal programming convention and matches how arrays are numbered (Module 11).

Off-by-onei < 6 runs 6 times (0–5). i <= 6 runs 7 times (0–6) — usually a bug. Count the iterations, not the last value.

The while loop

Use while when you don't know the count in advance — "keep going until something happens." This is the heart of capacitive sensing: charge a pad and count loops until it reads HIGH.

int ticks = 0;
while (digitalRead(padPin) == LOW) {   // until the pad charges to HIGH...
  ticks++;                              // ...count how long it takes
}
// a finger adds capacitance → charges slower → higher tick count
Infinite loopA while whose condition never becomes false runs forever and freezes the board. Make sure something inside can change the condition (here, the pad eventually charges).

Module 9

Functions

A function is a named, reusable block of code. You've been calling functions (digitalWrite, delay) since Module 4; now you'll write your own. This keeps loop() readable and avoids repetition.

// returns the tick-count for one pad
int readPad(int pin) {
  int ticks = 0;
  pinMode(pin, OUTPUT); digitalWrite(pin, LOW);   // discharge
  pinMode(pin, INPUT);                             // let it charge via pull-up
  while (digitalRead(pin) == LOW) ticks++;
  return ticks;                                    // hand the answer back
}

void loop() {
  int t = readPad(2);      // call it — reuse the logic for any pad
  Serial.println(t);
}

One definition, called as many times as you like — for pad 2, pad 3, or all six in a loop.

Reading a function signature

int readPad(int pin) unpacks as:

  • int (first) — the return type: it hands back an int. Use void if it returns nothing.
  • readPad — the name you call.
  • (int pin) — the parameter: an input you pass in, usable inside as pin.
  • return ticks; — sends a value back to whoever called it.
Why botherCompare "read pad 2, read pad 3, read pad 4…" written out six times (copy-paste bugs waiting to happen) versus one readPad() called in a loop. Fix a bug once, and it's fixed everywhere. setup() and loop() are themselves just functions Arduino calls for you.

Module 10

Digital input & the touch pads

Reading the world back in. The counterpart to digitalWrite is digitalRead(pin), which returns HIGH or LOW.

Input modes & pull-ups

An input pin left floating (connected to nothing) picks up noise and reads randomly. You need a known default, a pull. Two ways:

  • pinMode(pin, INPUT) — plain input; you supply an external resistor (like the R4/R5 10k pull-ups on your QPad's SDA/SCL lines).
  • pinMode(pin, INPUT_PULLUP) — turns on the RP2040's internal pull-up resistor, so the pin idles HIGH with no external part. This is why the touch pads on your board need no components — the chip pulls them up internally.
Connecting the datasheetFrom the RP2040 datasheet you read: an input reads HIGH above ~2 V and draws at most ~1 µA of leakage. That tiny leakage is why a pull-up resistor can quietly hold a pin at 3.3 V — the input barely loads it. Language and hardware meet exactly here.

How capacitive touch works, in code

There's no special "touch" function — it's built from primitives you already know. Discharge the pad LOW, switch to input, then count loops (a while) until the pull-up charges it to HIGH. A finger adds capacitance, slowing the charge, so the count rises:

int touchCount(int pin) {
  pinMode(pin, OUTPUT);
  digitalWrite(pin, LOW);          // drain any charge
  pinMode(pin, INPUT_PULLUP);       // now it charges through the internal pull-up
  int n = 0;
  while (digitalRead(pin) == LOW && n < 1000) n++;  // count, with a safety cap
  return n;
}

void loop() {
  int n = touchCount(2);
  if (n > TOUCH_THRESHOLD) Serial.println("touched!");
}

Note the n < 1000 guard in the while — it prevents an infinite loop if the pad never charges. Real embedded code always bounds its loops.

Module 11

Arrays: handle all six pads

An array is a numbered list of variables of the same type, under one name. Perfect for six pads.

// the GPIO pins wired to the six pads (example numbers)
const int padPins[6] = { 1, 2, 3, 4, 26, 27 };
int counts[6];   // room to store six results

Access elements by index, starting at 0:

padPins[0]   // → 1  (the FIRST element)
padPins[5]   // → 27 (the SIXTH / last element)
Zero-indexedA 6-element array has indexes 0–5. There is no padPins[6] — reading it is "out of bounds" and gives garbage (or a crash). This is why for loops use i < 6, not i <= 6.

Arrays + loops: the whole board in four lines

for (int i = 0; i < 6; i++) {

Module 12

Libraries & the OLED (I²C)

You don't drive the OLED byte by byte — someone wrote a library for that. A library is reusable code you include and call. This is how you reuse the whole community's work.

Including a library

#include <Wire.h>               // I²C communication (built in)
#include <Adafruit_SSD1306.h>   // the OLED driver (install via Library Manager)

#include pastes the library's declarations into your sketch (no semicolon — it's a preprocessor directive, like #define). You install libraries once via Tools → Manage Libraries.

I²C = two wires, many devices

The OLED talks over I²C: two shared lines, SDA (data) and SCL (clock). On your QPad those are GPIO6/GPIO7 (D4/D5), and R4/R5 are their required pull-ups. Each device has an address (the SSD1306 is usually 0x3C) so several can share the same two wires.

Adafruit_SSD1306 display(128, 64, &Wire);   // 128×64 px, using the Wire (I²C) bus

void setup() {
  display.begin(SSD1306_SWITCHCAPVCC, 0x3C);   // start it at address 0x3C
  display.clearDisplay();
  display.setTextSize(2);
  display.setTextColor(SSD1306_WHITE);
  display.setCursor(0, 0);
  display.println("Yui is cool!");
  display.display();   // nothing shows until you call display()!
}

The object display bundles data + functions. display.clearDisplay() means "call clearDisplay on this display" — the dot is how you use a library object, exactly like Serial.println.

Forgot the updateLibrary drawing calls (println, drawPixel…) only change an off-screen buffer. Nothing appears until display.display() pushes it to the screen. "My OLED is blank" is almost always a missing display.display().
Objects & the dotSerial and display are objects. The dot (.) calls a function that belongs to that object. You've used this since Module 6 — Serial.begin, Serial.println — it's the same pattern the OLED uses.

Module 13

Capstone: a touch instrument

Everything so far, in one sketch. Read all six pads, and when one is touched, print which one and show it on the OLED — without ever blocking. Read it top to bottom and name the concept each line uses.

#include <Wire.h>
#include <Adafruit_SSD1306.h>

const int padPins[6] = { 1, 2, 3, 4, 26, 27 };  // M11: array
const int TOUCH_THRESHOLD = 6;                          // M3: named constant
Adafruit_SSD1306 display(128, 64, &Wire);              // M12: library object

int touchCount(int pin) {                            // M9: function
  pinMode(pin, OUTPUT); digitalWrite(pin, LOW);        // M4: output
  pinMode(pin, INPUT_PULLUP);                          // M10: input + pull-up
  int n = 0;
  while (digitalRead(pin) == LOW && n < 1000) n++;   // M8: bounded while
  return n;
}

void setup() {                                       // M1: runs once
  Serial.begin(115200);                             // M6: serial
  display.begin(SSD1306_SWITCHCAPVCC, 0x3C);        // M12: I2C address
  display.setTextSize(2); display.setTextColor(SSD1306_WHITE);
}

void loop() {                                        // M1: runs forever
  for (int i = 0; i < 6; i++) {                   // M8/M11: loop over array
    int n = touchCount(padPins[i]);
    if (n > TOUCH_THRESHOLD) {                        // M7: decision
      Serial.print("pad "); Serial.println(i);
      display.clearDisplay(); display.setCursor(0,0);
      display.print("PAD "); display.println(i);
      display.display();                              // M12: push to screen
    }
  }
}
